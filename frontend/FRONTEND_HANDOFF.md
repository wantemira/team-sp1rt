# Текущее устройство фронтенда

Рабочие маршруты подключены к API в объединённой `main`. Старые демонстрационные
маршруты `/?view=...` заменены настоящими страницами; галерея находится в `/dev`.
Запуск и сценарии проверки описаны в [README.md](./README.md).

## Контракт

Префикс `/api/v1`. Деньги передаются строками рублей с двумя знаками;
ставка — процент годовых (20 означает 20%), срок — число месяцев.
Роли и владелец заявки определяются сервером. Публичной регистрации нет.
Фронтенд не назначает статус, скоринг, риск-грейд, ставку или лимит.

- Создание: POST applications, продукт term_loan.
- Каталог: GET products; min_amount/max_amount — строки рублей, terms — массив сроков.
- Черновик: PATCH applications/{id}, поля и актуальная version.
- Отправка/согласие: POST applications/{id}/submit и /sign, JSON с version.
- Дозаполнение: POST applications/{id}/fill, business_data и version.
- Проверки: POST employee/applications/{id}/retry-checks, JSON с version.
- Решение: POST employee/applications/{id}/action, uppercase action,
  version, comment, reason и/или approved_amount/missing_fields.
- Документ: POST applications/{id}/documents с FormData; скачивание
  GET applications/{id}/documents/{document_id}/file с JWT.

После изменения используется версия из ответа. При 409 перечитывается
карточка; пользователь снова проверяет данные или условия. При 401 сессия
сбрасывается. При ошибках валидации введённые значения сохраняются;
после конфликта черновика загружается актуальная версия сервера. Если
перечитать её не удалось, отправка и согласие блокируются до обновления. Черновик
после сохранения адресуется параметром `?draft=id`, а не общим localStorage.

## Предложение

`offer` доступно у APPROVED/ISSUED и содержит:
kind (ORIGINAL/COUNTER_OFFER), amount, annual_rate_pct, term_months,
monthly_payment, dscr, requested_dscr, target_dscr, monthly_cash_flow,
existing_debt_payments, max_total_debt_service, explanation.

UI отображает готовое предложение; самостоятельно платёж и лимит не считает.
Согласие доступно только при SIGN в next_actions и наличии offer. Модальное
окно повторяет сохранённые условия. При конфликте версии требуется повторное
подтверждение. ISSUED обозначает имитацию выдачи.

## Кабинет сотрудника

Виртуальные фильтры QUEUE/REVIEW/HISTORY разворачиваются в запросы конкретных
статусов: MANUAL_REVIEW; CHECKING/NEEDS_INFO; APPROVED/REJECTED/ISSUED.
Ответы объединяются по id. Карточка использует client.company_name, checks,
scoring_result.factors/rules_version, status_history и next_actions.
При техническом MANUAL_REVIEW сервер разрешает повтор проверок. Сумму
ручного одобрения и комментарий вводит сотрудник; безопасную ставку и
допустимость платежа рассчитывает backend. Произвольная ставка не отправляется.
Лимиты ручной суммы берутся из каталога; превышать запрошенную сумму нельзя.
На время операции поля и закрытие окна заблокированы. В истории решений
доступно сохранённое предложение с суммой, ставкой и платежом.
Последняя попытка каждого источника определяется по id; прежние попытки
раскрываются отдельно и не влияют на отображение текущего результата.

В общей информации сотрудник видит выручку и операционные расходы за
12 месяцев, месячный поток, текущие платежи и число активных кредитов,
задержанные платежи относительно всех платежей и текущую просрочку.
Данные берутся из `scoring_result.inputs`: ФНС имеет приоритет перед
сохранёнными данными клиента. Возле выручки и расходов указан источник.
Месячный поток отображается как `(выручка − расходы) / 12` с точным
округлением до копейки через BigInt; лимит, ставку и решение считает сервер.
Если снимка расчёта нет, показываются только последние полученные проверки
и данные заявки с соответствующей подписью. Старые успешные попытки не
подменяют текущий сбой. Нулевые обязательства, отсутствие истории и отсутствие
данных отображаются раздельно; непригодные источники сопровождаются пояснением.

Документы принадлежат конкретной заявке и скачиваются с сервера. Кнопки
несуществующего серверного удаления нет. В очереди есть явное обновление;
карточка клиента опрашивается раз в пять секунд без параллельных запросов
до конечного результата. Ошибка опроса предлагает повторить загрузку.

## Границы проверки

Модульные тесты проверяют адаптер, ошибки, денежные границы и актуальность
попыток проверок. Браузерные тесты основного пути, документов и повтора
источников используют настоящий API. Редкие ручные решения, конфликты версий
и изменённый каталог дополнительно проверяются с подменой ответов API;
они не подтверждают корректность банковской модели на сервере.
Для браузерных тестов нужен работающий API и отдельная синтетическая база.
Проверяется мобильный экран клиента и сотрудника шириной 390 px.
Общий Compose находится в корне: frontend/Nginx → API → PostgreSQL.
Раздельный прогон Vite/API проверяет HTTP-контракт; контейнерную сборку
проверяют отдельно по корневому README.

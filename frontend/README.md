# Кредитный кабинет

React/Vite: кабинет клиента и рабочее место сотрудника. Рабочие страницы
используют настоящий HTTP API; данные банка и внешние проверки на стенде
синтетические. Подписание и выдача смоделированы.

## Запуск двух веток до объединения

1. В отдельной рабочей копии ветки `API` подготовьте `.env` по `.env.example`,
   задайте локальные пароли и запустите `docker compose up --build`.
   Backend должен быть доступен на `http://localhost:8000`.
2. В рабочей копии `frontend-manager`:

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://localhost:5173`. Требуется Node.js 22.12+ либо 24 LTS;
проверенный Node.js 20.20 также соответствует требованиям текущего Vite.
Для API на другом адресе задайте `CREDIT_API_TARGET` при запуске Vite.

После объединения Docker-сборка фронтенда использует сервер `api:8000`
в общей Docker-сети. В этой ветке нет общего Compose: он находится в API.

## Проверочный путь

- Войдите как `demo.ip@example.com`. Пароль — `TEST_USERS_PASSWORD` из `.env`
  backend; при повторном seed пароль существующего аккаунта не сбрасывается.
- Выберите оборотный кредит, введите 1 000 000 ₽ на 24 месяца. ИНН берётся
  из профиля банка. Черновик можно сохранить и открыть после перезагрузки.
- Отправьте заявку. Сервер вернёт встречное предложение около 610 тыс. ₽,
  рассчитанные ставку и платёж, объяснение и безопасный денежный поток.
- Нажмите «Согласен с предложением», проверьте условия и подтвердите.
  После перезагрузки согласованные условия и результат сохраняются.
- `test.client2@example.com` показывает отказ с причиной.
- `test.client3@example.com` получает таймаут ФНС при первой отправке.
  Войдите как `test.employee1@example.com`, повторите проверку в очереди.
  Затем клиент может указать запрошенную выручку и получить новый результат.
  Пароль всех seed-аккаунтов задаётся одной настройкой backend.

Каталог, допустимые суммы и сроки загружаются из `/products`. При недоступных
условиях создать заявку или открыть ручное одобрение нельзя; есть повтор загрузки.

Проверки синхронные: интерфейс сначала ждёт сохранения параметров, затем —
результат ФНС/БКИ и расчёт сервера. Промежуточные успешные проверки
не выдумываются UI. Последние результаты источников показаны отдельно
от предыдущих попыток. При конфликте с недоступной текущей версией действия
блокируются до обновления заявки.

## Проверки разработки

```bash
npm run lint
npm test
npm run build
npx playwright install chromium
# Backend должен быть запущен с синтетическими аккаунтами:
E2E_PASSWORD=ваш_пароль npm run test:ui
```

Браузерные тесты создают синтетические заявки и документы. Запускайте их
на отдельной тестовой базе. `E2E_PASSWORD` по умолчанию равен `password123`.
Можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE`, `PLAYWRIGHT_BASE_URL` и
`FRONTEND_PORT` для изолированного прогона. Проверяются встречное предложение,
согласие и перезагрузка, отказ/чужая заявка, повтор проверки/дозаполнение,
содержимое загруженного документа, авторизация и доступность компонентов.

`employee-actions.spec.js` проверяет контракт интерфейса ручных решений
на подменённых ответах API: запрос сведений, отказ, ограничения суммы,
ошибку политики, конфликт версии и блокировку повторной отправки.
Авторизация остаётся настоящей. Эти тесты не проверяют серверный скоринг;
реальный повтор внешней проверки покрыт `employee-flow.spec.js`.
В `client-states.spec.js` ожидание отправки проверяется на настоящем API,
а редкие конфликты черновика и согласия — на подменённых версиях ответов.
`products.spec.js` подменяет условия каталога для проверки изменённых лимитов
и ошибок загрузки; сохранение корректного черновика идёт в настоящий API.

Описание модулей и API: [FRONTEND_HANDOFF.md](./FRONTEND_HANDOFF.md).
Галерея компонентов доступна на `/dev`. Примеры в `src/demo` используют
fixtures; рабочие страницы их не импортируют. Шрифт Inter поставляется
локально. Дизайн — концепт для хакатона, не официальный интерфейс банка.

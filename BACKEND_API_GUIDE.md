# Backend API: эндпоинты и логика приложения

Документ описывает backend, который сейчас находится в репозитории. Базовый
адрес локального API: `http://localhost:8000/api/v1`.

Для подробных типов запросов и ответов см. [Api.md](./Api.md) и
[api.yaml](./api.yaml). Эта инструкция дополнительно объясняет, что выполняет
приложение и какие ограничения есть у текущей реализации.

## Продукт и состояния

Поддерживается один продукт: `term_loan` — «Кредит на оборотные средства».
Сумма составляет 100 000–5 000 000 рублей, срок — 6, 12 или 24 месяца; выдача
одна, срок фиксированный, платежи аннуитетные. Суммы хранятся в `Numeric`,
считаются через `Decimal` и передаются в JSON строками рублей.

Статусы заявки: `DRAFT`, `CHECKING`, `NEEDS_INFO`, `MANUAL_REVIEW`, `APPROVED`,
`REJECTED`, `ISSUED`. При синхронной обработке `CHECKING` записывается в
историю как промежуточный переход в рамках транзакции, а ответ уже содержит
итоговый статус.

## Общая схема работы

```text
HTTP-запрос
  → маршрут FastAPI: app/api/routes/
  → проверка авторизации и роли: app/api/dependencies.py
  → бизнес-логика: app/services/
  → SQL-запросы: app/repositories/
  → PostgreSQL
```

Данные хранятся в таблицах `users`, `clients`, `employees`, `applications`,
`application_status_history`, `application_checks` и
`application_documents`. SQLAlchemy-модели находятся в [app/models/](./app/models/),
схемы запросов и ответов — в [app/schemas/](./app/schemas/).

Защищённые маршруты требуют заголовок:

```http
Authorization: Bearer <access_token>
```

Пользователь и его роль берутся из проверенного JWT и повторно сверяются с
пользователем в БД. `client_id`, статус заявки, историю и результаты решений
клиент не назначает самостоятельно.

## Аутентификация

### `POST /auth/login` — вход

- Публичный маршрут; JWT для запроса не нужен.
- Принимает `email` и `password`.
- Ищет пользователя по email и проверяет пароль по хешу `users.password_hash`.
- При успехе возвращает JWT, пользователя и связанный профиль клиента или
  сотрудника.
- Неизвестный email и неверный пароль возвращают одинаковую ошибку `401`.
- Регистрация через API отсутствует.

### `GET /auth/me` — текущий пользователь

- Требует JWT.
- Возвращает `user` и связанный профиль из `clients` или `employees`.
- Если токена нет, он просрочен, подпись неверна или пользователь/роль больше
  не совпадают с БД, возвращается `401`.

### Проверка доступа

- Клиентские маршруты заявки требуют роль `client`.
- Очередь, карточка и решения по заявкам требуют роль `employee`.
- Ошибка роли возвращает `403`.
- Чужая клиенту заявка намеренно возвращает `404`, не раскрывая, существует ли
  она у другого клиента.

## Клиентские маршруты

### `GET /products` — доступный продукт

Возвращает статическое описание единственного продукта MVP: `term_loan`,
диапазон суммы и доступные сроки. В текущей реализации это фиксированные
значения в коде, а не список, загружаемый из БД.

### `GET /news` — новости кабинета

- Требует роль `client`.
- Возвращает статическую приветственную новость для текущей версии MVP.
- Новости не хранятся в БД и не персонализируются по данным клиента.

### `POST /applications` — создание черновика

- Требует роль `client`.
- Принимает `product_type`; поддерживается только `term_loan`.
- Для создания достаточно:

  ```json
  {"product_type": "term_loan"}
  ```

- Сумма и срок на этом шаге необязательны и сохраняются как `null`, если не
  переданы.
- Если финансовых данных нет, `business_data` хранится как
  `{"financials": {}}`. Незаполненные доходы/расходы не заменяются нулями.
- `client_id` определяется по профилю авторизованного пользователя.
- Новая заявка получает статус `DRAFT` и начальную версию `1`.
- Одновременно создаётся первая запись истории: `previous_status = null`,
  `new_status = DRAFT`, `changed_by = CLIENT`.

### `GET /applications` — список заявок клиента

- Требует роль `client`.
- Возвращает все заявки текущего клиента, включая черновики.
- Список отсортирован от новых заявок к старым.
- При отсутствии заявок возвращается пустой массив.

### `GET /applications/{id}` — данные своей заявки

- Требует роль `client`.
- Возвращает карточку заявки только если она принадлежит профилю текущего
  клиента.
- Для отсутствующей или чужой заявки возвращается `404`.

### `PATCH /applications/{id}` — изменение черновика

- Требует роль `client` и владение заявкой.
- Изменять можно только заявку со статусом `DRAFT`.
- В запросе обязательна текущая `version`. Ответ содержит увеличенную версию.
- Можно передать сумму, срок, цель или финансовые данные.
- Пустое тело изменений отклоняется; неизвестные поля не принимаются.
- Статус остаётся `DRAFT`. Редактирование не добавляет запись в историю
  переходов статуса.
- Устаревшая версия или попытка изменить заявку не в `DRAFT` возвращает `409`.

### `POST /applications/{id}/submit?version={version}` — отправить черновик

- Требует роль `client`, владение заявкой и текущую версию.
- Разрешено только для `DRAFT`.
- Сумма обязательна и должна быть в диапазоне 100 000–5 000 000 рублей; срок
  обязателен и должен быть `6`, `12` или `24` месяца. Нарушения дают `422`.
- Сервис синхронно получает результаты моков ФНС/БКИ, вызывает
  `evaluate_credit(...)`, сохраняет обе проверки, score, итоговый статус и
  историю переходов (`DRAFT → CHECKING → итог`) одной транзакцией.
- Отсутствующие финансовые сведения дают `NEEDS_INFO`; `TIMEOUT`/`ERROR`
  внешней проверки — `MANUAL_REVIEW`.
- Если скоринг или сохранение завершается неожиданной ошибкой, транзакция
  откатывается, включая статус, проверки и историю. Заявка не остаётся
  навсегда в `CHECKING`.

### `POST /applications/{id}/fill` — заполнить сведения

- Доступно клиенту-владельцу только в `NEEDS_INFO`.
- Нужно передать каждое корректное значение, перечисленное в карточке
  `missing_fields`; заполнение только незапрошенных полей отклоняется.
- В теле запроса передаётся текущая `version`.
- После заполнения `missing_fields` и `info_comment` очищаются. Данные дополняют
  существующий `business_data`, после чего проверки ФНС/БКИ и
  `evaluate_credit(...)` запускаются синхронно в той же транзакции, что и
  переходы статуса.
- Возможный результат — `NEEDS_INFO`, `MANUAL_REVIEW`, `APPROVED` или
  `REJECTED`; ответ содержит карточку, проверки и историю.

### `POST /applications/{id}/sign?version={version}` — подписать договор

- Доступно клиенту-владельцу только для заявки `APPROVED`.
- Атомарно переводит заявку в `ISSUED`, сохраняет `signed_at`, `issued_at` и
  переход `APPROVED → ISSUED`. Это имитация подписания и выдачи; реальная ЭП и
  перечисление денег не интегрированы. Статуса `SIGNED` нет.
- Повторная подпись уже выданной заявки возвращает `409`, не меняя время
  выдачи и не добавляя запись в историю.

### `POST /applications/{id}/documents` — загрузить документ

- Требует роль `client` и владение заявкой.
- Принимает multipart-поля `document_type` и `file`.
- Метаданные записываются в `application_documents`; файл сохраняется на диске
  сервера в каталоге `UPLOAD_DIR` (в Docker — подключённый volume).
- По умолчанию допустимый размер — до 10 MiB; предел настраивается
  `MAX_UPLOAD_SIZE_BYTES`.
- Пустой файл отклоняется. Заявка со статусом `REJECTED` не принимает документы.
- Ссылка `file_url` ведёт на защищённый endpoint скачивания.

### `GET /applications/{id}/documents/{document_id}/file` — скачать документ

- Требует действительный JWT.
- Клиент может скачать файл только из собственной заявки.
- Сотрудник может скачать файл по заявке.
- Путь к файлу выбирает сервер по ID документа, а не клиентский запрос.

## Маршруты сотрудника

### `GET /employee/applications?status=...` — очередь заявок

- Требует роль `employee`.
- Возвращает заявки с одним выбранным статусом.
- Допустимые значения: `MANUAL_REVIEW`, `CHECKING`, `NEEDS_INFO`,
  `APPROVED`, `REJECTED`, `ISSUED` (последние три — история).
- Если `status` не указан, используется `MANUAL_REVIEW`.
- Черновики `DRAFT` в этот список не входят.

### `GET /employee/applications/{id}` — карточка заявки

- Требует роль `employee`.
- Возвращает заявку, профиль клиента, историю переходов, документы и записи
  `application_checks`.
- Для отсутствующей заявки возвращается `404`.

### `POST /employee/applications/{id}/action` — решение сотрудника

- Требует роль `employee`.
- В запросе указываются `action` и текущая `version`.
- Возможные действия:
  - `APPROVE` переводит заявку в `APPROVED`; требуются
    `approved_amount` и `comment`. Сумма должна быть положительной и не выше
    запрошенной суммы или лимита продукта. `approved_rate` автоматически
    устанавливается в 28% годовых; переданное значение должно быть `28`.
    Стоп-факторы (неактивная компания, возраст менее 12 месяцев или текущая
    просрочка) блокируют одобрение. Запрошенный срок не меняется.
  - `REJECT` переводит заявку в `REJECTED`; требуются `decision_reason_code`
    и `comment`.
  - `REQUEST_INFO` переводит заявку в `NEEDS_INFO`; требуются `missing_fields`
    и `comment`. Сейчас можно запросить только финансовые поля
    `business_data.financials.annual_revenue` и
    `business_data.financials.annual_expenses`. Также сервис требует
    `decision_reason_code`.
- В `application_status_history` записываются переход, комментарий и ID
  сотрудника (`changed_by_user_id`); `changed_by` назначается сервером как
  `EMPLOYEE`.
- Решения доступны только из `MANUAL_REVIEW` после успешного получения всех
  обязательных проверок. При техническом сбое разрешён только `RETRY_CHECKS`.
  Устаревшая версия или неверное состояние возвращает `409`.
- `next_actions` вычисляется для роли текущего пользователя: клиенту в `DRAFT`
  доступны `EDIT` и `SUBMIT`, в `NEEDS_INFO` — `FILL`, в `APPROVED` — `SIGN`;
  сотруднику при кредитном `MANUAL_REVIEW` доступны `APPROVE`, `REJECT`,
  `REQUEST_INFO`, при технической причине — `RETRY_CHECKS`. В остальных
  сочетаниях возвращается пустой список.

### Версия и результат расчета

- `version` начинается с `1` и проверяется и увеличивается атомарно через
  optimistic locking БД при изменении заявки. Устаревшая версия возвращает
  `409`.
- `scoring_result` хранит полный JSON последнего расчета (модель, статус,
  score, причина, финансовые данные, ответы проверок и факторы решения).
  `score`, `risk_grade`, `approved_amount` и `approved_rate` остаются
  самостоятельными сохраняемыми полями заявки.

### `POST /employee/applications/{id}/retry-checks` — повтор проверок

- Требует роль `employee`, текущую `version` и статус `MANUAL_REVIEW`.
- Доступен только при технической причине `EXTERNAL_CHECK_UNAVAILABLE`, если
  последняя попытка проверок содержит `TIMEOUT` или `ERROR`;
  успешный повтор не становится повторно доступным из-за старой ошибки.
- Запускает новый синхронный цикл проверки и скоринга, добавляет новые строки
  проверок и историю в одной транзакции.
- Повторная техническая ошибка оставляет заявку в `MANUAL_REVIEW` с технической
  причиной, а не фиксирует кредитный отказ.
- Попытка ФНС для `test.client3@example.com` определяется количеством проверок
  ФНС именно этой заявки в БД: первая даёт `TIMEOUT`, повторная — `SUCCESS`.
  Счётчик не хранится в глобальном состоянии процесса.

## Моки и кредитный расчёт

- Моки находятся в `app/integrations/fns_mock.py` и
  `app/integrations/bki_mock.py`; сервер выбирает профиль по синтетическому
  `clients.inn`. Клиент не передаёт сценарий проверки.
- `test.client1@example.com`: активная компания, возраст 36 месяцев, просрочки
  нет, платежи 50 000 ₽/мес.
- `test.client2@example.com`: активная компания, возраст 6 месяцев, просрочка
  10 дней, платежей нет.
- `test.client3@example.com`: профиль как у первого; первый вызов ФНС по каждой
  заявке — `TIMEOUT`, последующие — `SUCCESS`.
- Неуказанные ИНН используют нейтральный успешный профиль.
- `demo.ip@example.com`, ИНН `770000000001`: синтетический ИП с годовой
  выручкой 6 млн ₽, расходами 4.8 млн ₽ и платежами 43 тыс. ₽/мес. Запрос
  1 млн ₽ на 24 месяца даёт counter-offer около 610 тыс. ₽. Пароль —
  `TEST_USERS_PASSWORD`, как у остальных seed-аккаунтов.
- Пять факторов нормированы в 0–100, ставка зависит от демонстрационной PD,
  безопасная сумма обеспечивает DSCR >= 1.35. Политика и допущения:
  [CREDIT_POLICY.md](./CREDIT_POLICY.md). Это не откалиброванная банковская модель.
- Неактивный/молодой бизнес и текущая просрочка проверяются отдельно от балла.
  Успешно полученные неполные данные приводят к дозаполнению или ручному
  рассмотрению; недоступность источника не является кредитным отказом.
- `scoring_result` сохраняет версию правил, дату, входы, PD, пять факторов
  и `offer`: запрошенное покрытие, безопасные сумма/ставка/платёж, итоговый
  DSCR и объяснение. Одобренные сумма и ставка сохраняются также отдельно.
- При наличии финансовых показателей в серверном моке клиент не может их
  заменить вводом формы. Legacy-профили без выручки запрашивают её у клиента;
  расходы в этих синтетических профилях составляют 3 млн ₽/год.
- Подписание невозможно без положительной одобренной суммы и ставки;
  согласие сохраняет рассчитанные условия. Повторное согласие возвращает 409.

## Служебный маршрут

### `GET /health/db`

Проверяет соединение с БД простым запросом `SELECT 1`. Возвращает
`{"db": "ok"}`, если соединение доступно; используется для проверки состояния
сервиса. JWT не требуется.

## Ошибки

HTTP- и ошибки валидации возвращаются в едином формате:

```json
{
  "error_code": "CONFLICT",
  "message": "Описание ошибки",
  "details": null
}
```

Типичные статусы:

- `400` — бизнес-операция недопустима, например повторное решение финальной
  заявки.
- `401` — отсутствующий, неверный или истёкший токен либо неверные учётные
  данные.
- `403` — недостаточная роль.
- `404` — заявка/документ не найден или недоступен этому клиенту.
- `409` — неверное состояние заявки или устаревшая версия.
- `413` — превышен лимит размера файла.
- `422` — неверные поля запроса или отправка черновика без суммы/срока.
- `500` — серверная ошибка, например отсутствующий профиль у существующего
  пользователя.

## Тестовые аккаунты Docker

В конфигурации Docker Compose при старте создаются три клиента и два сотрудника.
Общий пароль задаётся через `TEST_USERS_PASSWORD` в `.env`. Создание
идемпотентно; существующие пароли не перезаписываются. Эти аккаунты предназначены
только для локальной разработки.

## Что пока не делает backend

- Не регистрирует пользователей через API.
- Не подключает реальные ФНС/БКИ или промышленный скоринг; используются только
  серверные моки и временная заглушка оценки.
- Не рассчитывает процентную ставку или одобренный лимит в автоматическом
  скоринге; решения сотрудника могут записывать эти поля отдельно.
- Не содержит отдельного API для администрирования пользователей, сотрудников,
  новостей или тестовых аккаунтов.
- Не предоставляет logout с отзывом JWT; клиентская сторона должна удалить
  сохранённый токен.

Основной контракт версии для submit/sign/retry-checks — JSON `{"version": 2}`;
старый query временно поддерживается. В карточке доступно типизированное поле
`offer` из сохранённого scoring_result. Подробнее: [Api.md](./Api.md).
